# Final backend security review — 2026-10-16

Scope: final source inspection of src/plugins.rs, src/plugin_runtime.rs and src/plugin_guard.rs; no reviewed code was changed by this reviewer. Backend owner was still landing the catalog update fallback during inspection.

## Result

No new confirmed P1/P2 vulnerability was found in the inspected final backend. This is a source review, not a replacement for root's native navigation and installation evidence.

## Security boundaries checked

- ZIP bytes are limited before opening; entry count, normalized case collisions, traversal/absolute/Windows path forms, reserved names, executable suffixes, symlinks and special modes are rejected. Each file is checked both by advertised size and bounded actual read; expanded total is bounded. Root manifest and referenced entry must exist. Unsafe conflicting file/directory structures fail during staging before replacement. Extraction uses validated relative names and ordinary file writes, so archive mode flags do not create links.
- Manifest ID is a bounded stable lowercase reverse-domain identifier. Required strings, exact API version, three-component u32 versions, host minimum, type, widget entry, known permission fields, network origins and URLs are checked. Theme functions are allowlisted; CSS escapes/comments/resource functions are denied; backgroundImage refers to an existing package raster asset. Uppercase extensions are normalized in bundle MIME dispatch.
- Installation validates before publishing. Stage content is fully written before moving the old installation aside. Failure to publish restores old files; failure saving the new registry removes the new destination and restores the backup. Settings live under plugins/data/ID independently of layout and are untouched by replacement. Settings and registry save via a sibling temp file plus rename. Power-loss/crash durability is not proven; no fsync/recovery journal exists, so do not advertise crash-consistent transactions.
- Settings, metrics and fetch require an installed enabled ID; metrics checks the actual manifest permission. Trusted-window IPC gate remains a second boundary behind the opaque-origin iframe broker; broker identity comes from bound source/instance/nonce, not a caller-provided plugin ID. SDK has no arbitrary invoke channel. Registry is host-owned local trusted state: list() does not revalidate every persisted manifest, but a local attacker able to rewrite that file already controls the same account's files. No remotely supplied archive path into registry state bypassing validate_manifest was established.
- Preview compares expected_id for update/catalog packages and checks SHA256 before creating a token. Commit rereads and revalidates staged bytes. Update metadata checks ID, version, HTTPS URL and 64-character hexadecimal hash; frontend supplies expectedId when previewing the returned package. The fallback catalog path was being finalized by backend and should remain covered in final integration tests.
- Network requests disable environment proxies and automatic redirects. Every hop checks authorized HTTPS origin, resolves all addresses, rejects private/reserved targets, and supplies those exact addresses to reqwest via resolve_to_addrs. HTTPS hostname/certificate validation stays enabled. The body and redirect count are bounded. DNS resolution itself uses system getaddrinfo before reqwest's connect/request timeouts; this source review does not claim a hard wall-clock bound covering OS DNS resolution.
- Native guard registers FrameNavigationStarting once per HWND, allows only exact about:blank/about:srcdoc, cancels all other subframe navigation, and clears cache on window destruction. plugin_bundle awaits successful registration before handing code to the host. Package code cannot create an allowed top-navigation capability: sandbox permits scripts only; child frames are blocked by CSP. Actual WebView callback coverage must be proven using native navigation probes; source inspection alone cannot establish it.

## Evidence and limits

Existing backend source tests cover traversal, duplicate/case paths, symlink modes, file count, individual/total expansion, incompatible API/version, network denial, theme resource restrictions and rejected update preserving files/data. They were inspected, not independently rerun while root/backend were building. The update rollback test injects invalid staged bytes, rather than forcing a registry-save failure; the latter branch was reviewed directly.

Independent developer-tool parity checks: Python packager expanded Windows reserved names to match backend (CONIN$/CONOUT$/COM0/LPT0, superscript COM/LPT digits, trimmed stems). An initially failing path test passed after alignment. Final `python -m unittest discover -s tests -p test_plugin_packaging.py`: 10 pass. Existing plugin UI security/lifecycle Node suite passed during review. No production account, remote server or personal configuration was modified by this reviewer.

Actual WebView checks confirm theme raster background apply/restore, SDK-ready execution in opaque sandbox, forged-message rejection, large-size transition, disable/re-enable frame lifecycle, uninstall frame destruction, HTTPS catalog/package reinstall with SHA and expected-ID preview, private-settings preservation and existing layout-slot restoration. Node security and lifecycle suite rerun after freeze: pass.

plugin_uninstall now emits plugins-changed immediately after the registry removal succeeds, before resource/data cleanup. Thus cleanup failure cannot leave a registered active capability or prevent clients from receiving teardown notification; subsequent active() calls reject the removed ID. Filesystem cleanup failure remains an error returned to the user. No new confirmed P1/P2 remains from this scoped review. No code was changed during this final review.
